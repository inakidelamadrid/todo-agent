## Findings

1. **Webhook handler error does not roll back `session` before `mark_update`** (note — PR #37, `api/app/telegram/webhook.py` lines 74–89): `claim_update` commits immediately, which is great, so the claim survives a handler failure. However, if a future handler flushes a failing DB statement on `session` and raises, `session` will be in a pending-rollback state when `repository.mark_update(session, ...)` executes on line 89, turning a handler failure into a 500 response to Telegram. Suggested follow-up ticket: add `await session.rollback()` in the `except Exception:` block of `receive_update` (with a regression test simulating a DB error inside a handler).
2. **`HANDLERS` registry is a mutable `dict`** (note — PR #37, `api/app/telegram/handlers.py` line 63): unlike `COMMANDS` (`routing.py`) and `TEMPLATES` (`templates.py`), which use `MappingProxyType`, `HANDLERS` is a plain `dict[str, Handler]` while ticket BE-015 specified `Mapping[str, Handler]`. Low risk while only core handlers exist; worth wrapping in `MappingProxyType` (or documenting the mutation convention) once feature handlers register.
3. **Large multi-ticket PRs & stale ticket statuses** (note — PR #37 bundled 9 tickets and left all 9 at `Status: todo`; PR #43 bundled 5 tickets across 24 files). Code quality is high, but smaller per-ticket PRs keep review scope aligned with `AGENT-DEV-PIPELINE.md` §4.
4. **`TestMessageTab.tsx` drops `ApiError.fieldErrors`** (note — PR #43, `web/src/features/playground/TestMessageTab.tsx` lines 35–41 & 66): `toOutcome` discards `e.fieldErrors`, so `fieldErrorsFrom` only runs its message-regex fallback. Today `POST /admin/telegram/test-message` returns `Missing field: <name>` which matches the fallback, so this is harmless now, but preserving `fieldErrors` in `SendOutcome` would keep it consistent with `useTemplatesStore.ts`.
5. **Minor: `fieldErrorsFrom` builds an unescaped `RegExp` from field names** (note — PR #43, `web/src/features/playground/templateForm.ts` line 24): template field names come from trusted server templates (`[a-z_]+`), so not exploitable, just worth noting if field syntax ever widens.
