## Goal

A `telegram_updates` table exists, keyed by Telegram's `update_id`, to remember which updates were already handled.

## Why this ticket exists

Telegram re-sends an update when our response is slow or fails. To process each one exactly once we must remember the ones we have seen. The table ships alone so the schema can be reviewed without any logic around it.

## Read first

- `api/app/bills/models.py`: column style, CHECK constraints mirroring the API rules.
- `api/migrations/env.py` line 20: models must be imported there to be seen by Alembic.
- `RUNBOOK-migrations.md`.

## Design

- **Pattern:** Idempotency key: the provider's own unique ID is our primary key, so the database itself refuses duplicates.
- **Data flow:** none yet; schema only.

**Table `telegram_updates`**

| Column | Type | Rules |
|---|---|---|
| `update_id` | `BigInteger` | primary key, not auto-generated |
| `chat_id` | `BigInteger` | nullable |
| `message_id` | `BigInteger` | nullable |
| `kind` | `String(20)` | CHECK: one of the `UpdateKind` values |
| `route` | `String(40)` | default `""` |
| `status` | `String(12)` | CHECK: `received`, `processed`, `failed`; default `received` |
| `received_at` | timestamptz | `server_default=func.now()` |

- Index `ix_telegram_updates_received_at` on `received_at` (used to delete old rows).
- No message text, caption or callback data is stored.

The epic's draft lists an `ignored` status. It is left out on purpose: BE-009 does not store ignored updates.
